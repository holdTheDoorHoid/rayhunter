# Compatibility With Upstream

If you are moving between this fork and upstream Rayhunter, in either direction,
or in a hurry, this is the page to read first. It is precise on purpose. The
short answer: **your raw recordings and your config are safe to move both ways;
the analysis report format is the one thing to handle deliberately, and
re-analysing a recording sidesteps it entirely.**

## The one-paragraph version

Raw recordings are a standard format and move freely between versions. Config
files do not error in either direction, each version ignores settings it does
not recognise and fills in defaults for settings it expects but does not find, though settings unique to one version are lost if the other saves the file. The
analysis report has a version number, and this fork writes a newer version than
upstream; because the raw recording is portable and re-analysis is cheap, the
safe move when switching is to **re-analyse the recording on whichever version
you are running** rather than relying on the report file to carry over.

## Recordings (raw captures)

**Fully compatible both ways.** The raw capture files, the `.qmdl` diagnostic
recording and the `.pcap` packet capture, are standard formats and are not the
fork's invention. A recording made on either version can be opened, analysed, or
inspected on the other, and in external tools like Wireshark. Moving the raw
recording is always safe.

One fork addition to note: this fork records 2G and 3G signalling into the
capture where upstream historically dropped it. A capture made here may therefore
contain more than an upstream one would, but nothing that makes it unreadable
upstream, the extra messages are standard, only present.

## Configuration files

**Compatible both ways, but lossy across the gap.** The config file is TOML, and
both versions read it the same forgiving way:

- **Fork reading an upstream config:** any setting the upstream file does not
  mention comes up at the fork's default. Detectors absent from an older file
  come up **on**, not off, so an upgrade never silently disables one, this is
  covered by a test in the fork.
- **Upstream reading a fork config:** settings unique to this fork (custom
  display colours, keep-screen-on, web accounts, rotation, and the rest) are not
  recognised and are ignored. Upstream runs fine; it does not act on them.

The catch is saving. If you move to upstream and it saves the config, the
fork-only settings it ignored are dropped from the file, because a saved config
is written from what the running version understands. Keep a copy of your config
before switching if you want those settings back later. [Configuration
Reference](../configuration-reference.md) lists which keys are fork-specific.

## Analysis reports (the one to handle deliberately)

This is the part that needs care. When Rayhunter analyses a recording, it writes
a report in a versioned format. **This fork writes report format version 3**,
which the [packet explorer](../packet-explorer.md) advanced in order to record,
for each finding, which exact message produced it.

- **This fork reads older reports fine.** It understands the older report
  formats (including upstream's) and normalises them, so reports made by upstream
  open here without trouble.
- **Upstream reading a fork report is the case to be careful with.** A version-3
  report carries a field that older versions did not. Whether a given upstream
  version reads it cleanly depends on that version, and this book cannot promise
  it for a version it does not control.

The reliable way around this is the same in both directions and does not depend
on any version's tolerance: **because the raw recording is portable, re-analyse
it on the version you are using.** Re-analysis regenerates the report in that
version's own format from the raw capture. [Re-analyzing
Recordings](../reanalyzing.md) covers how. Treat the report file as disposable
and the raw recording as the thing of record, and moving between versions holds
no surprises.

## Can you switch back?

Yes. Switching between the fork and upstream is reversible:

- Your **raw recordings** remain readable on either.
- Your **config** is read by either; keep a backup if you rely on fork-only
  settings, since a save on upstream drops them.
- Your **reports** are best regenerated by re-analysing on whichever version you
  land on.

There is no one-way door here. The thing to protect is the raw recordings; the
rest is either portable or regenerable.
